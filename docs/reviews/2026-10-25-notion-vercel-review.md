# Notion + Vercel architecture review (2026-10-25)

Two independent reviewers checked ONLINE-ARCHITECTURE.md against the official Notion, Vercel and Next.js docs. Accepted fixes are in ONLINE-ARCHITECTURE.md section 8.


## Review: notion

### Issues
- **[major]** The Free-workspace block limit is missing. Since 2026-09-08, a Free workspace with more than one member gets only 1,000 lifetime blocks through internal connections, and deleting does not give them back. The app creates about 66 pages per project plus one History row per change, so such a workspace locks up after roughly 10 projects with 403 restricted_resource (block_limit='block_creation').
  - Fix: Before building, ask the user which workspace and plan they will use. Document the requirement: a single-member Free workspace (guests are fine) or any paid plan. Map 403 with additional_data.block_limit to a plain message on Setup and in every write. Add this to the Setup checklist. Do not switch to a personal access token to dodge the limit, because a PAT carries the user's full permissions.
- **[major]** The 'Change a value' flow recomputes Cells, Progress and Current from a Steps query sent right after the PATCH. Notion has no transactions or conditional writes, and query freshness after a write is undocumented. Two quick changes to different steps of one project can also race on the Project page's Cells (last write wins). The Rev check is read-compare-write without an atomic guard. Portfolio would show wrong colours until the next write.
  - Fix: Serialise every Cells-affecting write per project in the client queue, not per node. Do not rebuild from a fresh query. Either overlay the PATCH response (pages.update returns the full page) onto the query rows, or read Project.Cells, change one cell and write it back. Add reconcile-on-open: the project page already queries all Steps, so recompute Cells, Progress and Current and PATCH the Project when they differ. Add a 'Repair mirrors' admin action. Describe Rev honestly as stale-tab detection only.
- **[major]** 'Each batch is idempotent' is false for creates. Notion has no idempotency key. A pages.create or databases.create that returns 503 or times out may already be saved, so a resumed batch can duplicate Steps, History rows or whole databases.
  - Fix: Give every created row a deterministic key property, for example Steps 'Step key' = <projectId>:<milestoneId> and History 'Event id' = a uuid made before the request. Each create batch first queries what exists and skips it. On 503, read additional_data.committed_resource_id or retry_guidance before retrying. Setup discovery must handle two databases with the same title: pick the one with the expected marker or schema and warn.
- **[minor]** Retries stack. SDK 5.28.0 already retries 429 and 529 (all methods) and 500/503 (GET/DELETE), twice by default, with maxRetryDelayMs of 60 s. A second home-made 5-retry layer can make 18 attempts and sleep for minutes inside one function call. 409 conflict_error is retried by neither layer.
  - Fix: Pick one layer. Either new Client({retry:false}) plus your own wrapper, or retry:{maxRetries:4, maxRetryDelayMs:10_000} plus only a concurrency gate (p-limit 3, with queries counted separately at about 3 rps). When Retry-After is longer than about 10 s, return 'Notion busy' so the client-driven batch can resume later. Handle 409 by re-reading, then retrying once.
- **[minor]** Writing Progress as 0-100 into a 'percent' number property displays as 5,800 %, because Notion multiplies by 100.
  - Fix: Write pct / 100 to Notion, or use the plain 'number' format. Keep the app's integer pct internally.
- **[minor]** Select mirrors (Customer, Project type, Type, State) rely on auto-created options. Option names cannot contain commas, so a value like 'Acme, Inc.' fails with validation_error. Page writes cannot set colours, and the docs give no ceiling for auto-created options.
  - Fix: Sanitise mirror names: replace ',' with ' ·' and truncate to about 100 characters. Pre-create State, Status, Flag, Kind, Source and Field type options with colours in the schema. When a new Customer or Project type choice is added in the app, add it with dataSources.update before writing pages.
- **[minor]** The dual relation's back-property on Projects may not be named 'Steps'. Its naming on create is undocumented. Projects pages will also carry 64+ Steps references, truncated to 25 with has_more in every page and query response, which bloats the Portfolio payload.
  - Fix: After creating Steps, read relation.dual_property.synced_property_id from dataSources.retrieve(Steps) and rename it with dataSources.update(projectsDs, {properties:{[id]:{name:'Steps'}}}). Never read Projects.Steps. Pass filter_properties on the Portfolio query and leave out Steps and Details. Flow is probably still needed, because 'current' depends on edges and today.
- **[minor]** 'Recorded = Notion created_time' loses seconds, because created_time is truncated to the minute. Sorting History newest-first by created_time leaves events from the same minute in unstable order.
  - Fix: Add a number property 'Seq' (epoch ms, plus a counter for ties within one correlation) and sort by Seq descending. Keep the exact ISO instant in the Data JSON. Treat created_time as display only.
- **[minor]** Schema access by property name is fragile. The user can rename properties or databases in Notion. Responses are keyed by name, and setup finds databases 'again by title'.
  - Fix: At setup, record the database and data source ids and every property id. Write using property ids as keys and map responses through the id field. Find databases by a stable marker (for example a description 'gunnebo-pm:steps', or ids saved after setup) and fall back to the title. Add a schema check and repair, using Settings schema.version. Optionally call databases.update({is_locked:true}) to discourage UI schema edits; the docs only say this locks editing in the Notion app UI.
- **[minor]** Runtime discovery is expensive on every cold start: one blocks.children.list plus seven databases.retrieve, about 8 requests per new Vercel instance. That uses rate budget and adds about 1-2 s.
  - Fix: Cache the discovered id map in the Next.js data cache (tagged, long-lived) or in an env var or Settings key written after setup. Re-discover only on 404 object_not_found.
- **[minor]** The Files plan conflicts with Notion's type allowlist and with the 302 download. Outlook .msg and .eml files are not supported and fail with 400. Section 5 promises Content-Disposition, an inline allowlist and CSP on downloads, but a 302 to Notion's signed URL serves Notion's own headers, not the app's.
  - Fix: Check the extension in the browser against Notion's list and suggest zipping or a SharePoint link for .msg and .eml. Either say plainly that downloads are a 302 to a 1-hour signed URL on Notion's host (a different origin, so no XSS risk to the app), or stream files of 4 MB or less through the route with the app's own headers and 302 only larger ones, such as files added in Notion directly.
- **[minor]** The 'Notion page history covers that' argument for append-only History is weak. Version history lasts only 7 days on Free (30 Plus, 90 Business). There is also no backup plan: this document supersedes DESIGN section 8 but replaces nothing, and Notion becomes the only copy.
  - Fix: State the retention by plan. Add an 'Export all data (JSON)' route using collectAllDataSourceRows, which also handles the 10,000-row cap, and point to Notion's workspace export as a second copy.
- **[minor]** Search-based parent discovery has gaps. Indexing is not immediate, and a title query matches substrings, which can include rows of the app's own databases.
  - Fix: Keep the exact-title match and require parent.type of 'workspace' or 'page_id', not 'data_source_id'. When several pages match, ask for NOTION_PARENT_PAGE_ID. Add a Refresh button on Setup. Prefer NOTION_PARENT_PAGE_ID when it is set and check it with pages.retrieve.
- **[minor]** Rate-limit notes are incomplete. The doc omits the per-workspace shared budget, whose Retry-After can exceed 60 s, and the query-specific 429 reasons.
  - Fix: Document both. Size batches adaptively: halve the batch on 429, and honour Retry-After before sending the next batch.
- **[minor]** The JSON-in-rich_text helpers have edge cases. The API rejects empty strings, Notion may merge or re-split text items on read, and a careless split at 2,000 can cut a surrogate pair.
  - Fix: textToRichText('') returns []. Split at 2,000 UTF-16 units or fewer and never between surrogate halves. richTextToText joins every item's plain_text regardless of item boundaries. Reject values over 100 chunks before sending. Keep the whole PATCH under about 400 KB, since JSON escaping inflates size, and test it against the fake.

The default name is not documented. [https://developers.notion.com/reference/property-object ; https://developers.notion.com/reference/update-a-data-source]

- (unclear) 'Notion queries are ~150-400 ms each': Not documented. Measure it in a spike. [https://developers.notion.com/reference/query-a-data-source]

### Implementation notes
- Client: new Client({ auth: process.env.NOTION_TOKEN, notionVersion: '2025-09-03', retry: { maxRetries: 4, maxRetryDelayMs: 10_000 }, timeoutMs: 30_000 }). 2025-09-03 is already the SDK default (Client.defaultNotionVersion). Use only in_trash, never archived, so a later move to 2026-03-11 is trivial.
- Setup order (each needs the previous data_source_ids): Settings, Project fields, Milestones, Projects; then Steps (Project dual_property relation to Projects, Milestone single_property relation to Milestones); then History, Notes and Files (single relations to Projects and Steps). After each databases.create, call dataSources.retrieve(data_sources[0].id) to collect property ids. Rename the auto-created back-relation on Projects via dataSources.update({data_source_id, properties:{[synced_property_id]:{name:'Steps'}}}).
- Relation definition: { type:'relation', relation:{ data_source_id, type:'single_property', single_property:{} } } or { ..., type:'dual_property', dual_property:{} }. Relation value write: { relation:[{id: pageId}] }. A write replaces the whole array, with at most 100 ids per request.
- Select definition: { type:'select', select:{ options:[{name:'Done', color:'green'}] } }. Value write: { select:{ name } } or { select:null }. Names may not contain commas, and unknown names auto-create an uncoloured option. Number: { number:{ format:'percent' } }; write 0.58 for 58 %.
- Query: notion.dataSources.query({ data_source_id, filter_properties?:[ids], filter:{ and:[ {property:projectRelId, relation:{contains:projectPageId}}, {property:archivedId, checkbox:{equals:false}} ] }, sorts:[{property:orderId, direction:'ascending'}], page_size:100, start_cursor }). select equals also accepts string[]. Compound filters nest at most 2 levels. Watch result.request_status?.type === 'incomplete' (10k cap). Paginate with collectPaginatedAPI(notion.dataSources.query, args), or collectAllDataSourceRows for exports.
- Relation and people values in any page or query response are capped at 25 (has_more is absent from the SDK types, so read it untyped). Use notion.pages.properties.retrieve({page_id, property_id, start_cursor, page_size}) only if a full list is ever needed.
- File upload in the route handler (Node runtime): const up = await notion.fileUploads.create({ mode:'single_part', filename, content_type }); await notion.fileUploads.send({ file_upload_id: up.id, file:{ filename, data: new Blob([buf], {type}) } }); then notion.pages.create({ parent:{type:'data_source_id', data_source_id: filesDs}, properties:{ [fileProp]:{ files:[{ type:'file_upload', file_upload:{id: up.id}, name: filename }] }, ... } }). Do it all within 1 hour, since unattached uploads expire and cannot be deleted. Reading back: files[i].type==='file' gives file.url and file.expiry_time (1 h).
- Discovery: notion.blocks.children.list({ block_id: parentPageId, page_size:100 }), filtering isFullBlock(b) && b.type==='child_database' (b.child_database.title). Then notion.databases.retrieve({database_id: b.id}) gives data_sources[0].id. Verify in a spike that block.id equals the database id. Parent lookup: notion.search({ query:'Gunnebo PM', filter:{property:'object', value:'page'}, page_size:100 }) with an exact-title and parent-type check.
- Errors: import { APIResponseError, APIErrorCode, isNotionClientError } from '@notionhq/client'. Handle restricted_resource with body.additional_data.block_limit==='block_creation' (workspace block limit), conflict_error 409 (re-read, retry once), service_unavailable on writes (check additional_data.committed_resource_id or retry_guidance), and object_not_found (not shared, or the ids cache is stale).
- Never send empty strings: clear rich_text with [], url, select and date with null, and a checkbox with false. Calendar dates write and read as 'YYYY-MM-DD' (date-only), which suits the string-compare design. Keep precise instants in JSON, because created_time is minute-truncated.
- Fake Notion must enforce the real limits so tests catch violations: 2,000 characters per text item, 100 items per array, 100 relation ids per write, 500 KB payload, page_size of 100 or less, 25-ref truncation with has_more, comma-free select names with auto-create, 2-level filter nesting, minute-truncated created_time, and optional injected 429/409/503-after-commit.
- SDK 5.28.0 also exposes pages.move, pages.retrieveMarkdown/updateMarkdown, views.* and dataSources.listTemplates. None are needed. pages.update also accepts is_locked and erase_content. Notion webhooks (data_source.content_updated) could invalidate caches after edits in Notion, but this is optional.
- Scratch verification: /tmp/claude-0/-home-user-gunnebo-pm/a41befe2-2647-55f4-b4fa-87a4fb1ee16d/scratchpad/review-notion/src/check.ts typechecks (tsc strict) every call shape above against @notionhq/client 5.28.0. Nothing in /home/user/gunnebo_pm was modified.


## Review: platform

### Issues
- **[major]** The plan does not choose a Vercel plan. Hobby terms allow 'non-commercial personal use only'. A tracker for Gunnebo customer orders (SITA, IDEMIA, NEC, Collins), used for the user's paid job, very likely counts as commercial. A plan change also moves several limits this design works around: cron frequency, 800 s duration, Skew Protection, multi-region, Password Protection. Separately, putting customer data in a personal Notion workspace and on Vercel may need employer approval.
  - Fix: Add a 'Plan' row to §1. Default to Pro ($20/month) for work use, or get written confirmation from Vercel support that Hobby is fine. Either way, design to Hobby limits so the app works on both. Add one line to the user summary asking them to confirm that company data may be stored in Notion and Vercel.
- **[major]** Backups and restore are gone. §8 of DESIGN.md (daily backups, keep 14, backup before import/reset, restore, 'Back up now' in Settings) is listed as superseded, but nothing replaces it. Notion page history (7 days on Free) and the trash are not backups. There is also no copy of attachments.
  - Fix: (1) A nightly GitHub Actions workflow (schedule such as '23 18 * * *' UTC, free, no 300 s cap). It runs scripts/backup-notion.ts with a separate read-only Notion integration token stored as a GitHub secret. It exports every data source to NDJSON plus downloads attachments (each ≤5 MiB), and commits to a private backup repo or uploads an artifact with 90-day retention. (2) A Settings 'Back up now' button that pulls pages through a server action and builds the zip in the browser, so the 4.5 MB response cap does not apply. Record lastBackupAt in Settings and warn after 48 h. (3) Before every template import or reset, store the current template export JSON as a Settings/History snapshot. (4) A documented, tested restore into a fresh parent page with an id-remapping table (Notion page ids cannot be chosen).
- **[major]** Reset is gone. DESIGN §8 and open question 12 promised 'reset:template' (Library + Template back to the seed, projects kept) and 'reset:all' (typed RESET, backup first). These were npm scripts and have no online counterpart.
  - Fix: Settings → 'Reset template to seed': run the seed through the existing importer in client-driven batches, after the automatic template snapshot. Settings → 'Start over': require typing RESET, run a backup, set in_trash:true on each app database through databases.update (recoverable for 30 days), clear the cached IDs, then rerun Setup. Write a History/system row before and after.
- **[major]** The append-only guarantee is only a policy. DESIGN used triggers that blocked UPDATE/DELETE. Online, anyone with Notion access can edit or delete History rows, and the stated fallback (page history) lasts 7 days on Free. 'Recorded = Notion created_time' is also rounded down to the minute, so history rows cannot be ordered reliably.
  - Fix: Make history tamper-evident and add deterrents. (a) Give each History row Seq (number: epoch ms × 1000 + counter), Prev hash and Hash = sha256(prevHash + canonicalJSON(row)), and add a 'Verify history' check (plus a unit test) that reports edits and gaps. (b) Set databases.update({database_id, is_locked:true}) on History and optionally pages.update({page_id, is_locked:true}) after each create (+1 request). (c) Rely on the nightly external backup in git as the immutable copy. (d) Order by Seq or Occurred at, never by created_time. Tell the user plainly that history is tamper-evident, not tamper-proof.
- **[major]** Atomic operations and idempotency are gone. DESIGN relies on single transactions (createProject, archive + reconnect with batch ids, insert-after, applySync with re-plan, import). Notion has no transactions. 'Each batch is idempotent' is claimed, but a retried value write duplicates its History POST. applySync re-plans on every batch, so items applied in earlier batches drop out of the plan and trip the 'selected id missing → abort' rule from §12.
  - Fix: Give every user action an opId (UUID) and every item a stable key. Before writing: GET the step, and if its 'Last op' property equals opId, skip the PATCH. Query History by an 'Op id' property before POSTing. For sync and import, persist a job record (Settings or project property 'Job': {opId, plannedItems with hashes, done[]}) once, then apply items from the job, not from a fresh plan. Fix the write order: Steps → Project Flow/Cells → History. Add a 'reconcile' routine (rebuild Cells/Progress from Steps, drop edges to missing or archived nodes) that runs on project open when Cells.version ≠ Steps max Rev.
- **[major]** The attachment limit drops from 50 MB (DESIGN Q17 default, approved by the user) to 4 MB, and attachments are left out of backups. This is not called out to the user. No workaround keeps files in Notion: Notion multi-part parts must be ≥5 MiB, Vercel request bodies are capped at 4.5 MB, and Notion Free allows only 5 MiB per file anyway.
  - Fix: Add this to the user-facing summary as a decision: 'Files up to 4 MB are stored in Notion. Bigger files go in as a SharePoint/OneDrive link.' Enforce the cap in the browser before upload and again in the route handler (file.size ≤ 4_000_000; reject early on Content-Length). Only if the user needs large files: Vercel Blob client uploads (browser → Blob directly), storing only the URL in Files & links. Back up attachments in the nightly job.
- **[major]** Preview deployments would use production data. 'Every other branch = preview URL', and Preview env vars apply to every non-production branch. If NOTION_TOKEN is scoped to Preview, unfinished builds write to the live Notion data, and Setup/bootstrap could change production database schemas. Previews would also share production's 3 rps budget. If Preview has no token, the fake Notion falls back to data/fake-notion.json, which cannot be written on Vercel (read-only filesystem; /tmp is per instance).
  - Fix: Use a second internal integration plus a 'Gunnebo PM (Preview)' parent page, with NOTION_TOKEN and NOTION_PARENT_PAGE_ID scoped to Preview only, seeded with demo data. Production gets its own Secret-type values. The fake is allowed only when !process.env.VERCEL. On Vercel without a token, always show the Setup page and never fall back to the fake. Mix VERCEL_ENV into the session key so preview cookies are not valid on production.
- **[major]** The session key design has weaknesses. (1) With SESSION_SECRET optional, the HS256 key is derived only from APP_PASSWORD through fast HKDF. Any leaked cookie then lets an attacker guess the password offline at GPU speed, and '≥12 characters' does not guarantee entropy. (2) Tokens are stateless, last 30 days and cannot be revoked. A stolen cookie gives full read/write on all customer project data, archive and import, and attachment downloads, for up to 30 days. It does not expose NOTION_TOKEN. (3) Rotating the password needs a redeploy. Older deployment URLs and Instant Rollback keep the old APP_PASSWORD and NOTION_TOKEN.
  - Fix: Make SESSION_SECRET (32 random bytes) required. Derive key = hkdfSync('sha256', SESSION_SECRET, sha256(APP_PASSWORD), 'gpm-session-v1:'+VERCEL_ENV, 32). The password then never becomes a cracking oracle, and changing either value revokes all sessions. Add an 'epoch' claim checked against Settings 'auth.epoch' (cached per instance for 60 s) for 'Sign out everywhere'. Use a sliding 7-day idle limit with a 30-day absolute cap. Name the cookie __Host-gpm_session (Secure, Path=/, no Domain). Turn on Standard or All Deployments protection so old deployment URLs stay closed. Document the kill switch: regenerate the Notion integration secret, then update env and redeploy. The README should have the user generate the password (e.g. openssl rand -base64 24) rather than choose one.
- **[major]** The login is exposed to brute force on a public URL. The 800 ms failure delay does nothing against parallel guesses: every request is a separate invocation, and Fluid compute scales to 30,000 concurrent. In-memory counters exist per instance only, and the design has no persistent rate-limit store.
  - Fix: Layer the defences. (1) Turn on Vercel Authentication → 'All Deployments', free on Hobby since 2026-09-09. Only the owner's Vercel login can then even reach /login, and the app password becomes the second factor. (2) Use the one Hobby WAF rate-limit rule: path = /login AND method = POST, 10 requests per 10 min per IP → 429. (3) Use a generated password of 20+ random characters. (4) Optionally keep a global failure counter in Settings ('n failed logins since your last visit' banner) that adds delay but never locks the owner out. Remove the claim that the delay prevents brute force.
- **[major]** The caching approach is unspecified and clashes with DESIGN. 'Library/template reads cached with tag invalidation' does not say how. 'use cache' requires cacheComponents, and with that on the force-dynamic exports from DESIGN §12 error, new Date() in prerender fails the build, and route state stays preserved by Activity. The default 'use cache' storage does not persist across serverless requests anyway. Caches also hide edits the user makes directly in Notion, which the architecture encourages ('data stays visible and filterable in Notion').
  - Fix: In Phase 1, leave cacheComponents off and keep force-dynamic plus connection(). Cache Library, project fields, template.flow and the discovered DB/data-source IDs with unstable_cache(fn, ['library', SCHEMA_VERSION], { tags: ['library'], revalidate: 60 }); this persists in Vercel's Data Cache per environment. Invalidate with updateTag('library') in Server Actions and revalidateTag('library', { expire: 0 }) in Route Handlers. Never use single-argument revalidateTag. Add a 'Reload from Notion' button. On object_not_found, drop the ID cache and rediscover.
- **[major]** The function region is not set, so it defaults to iad1 (Washington). Notion's US data lives in us-west-2 (Oregon). A value change makes about 4 sequential Notion round trips (GET step → PATCH step → Steps query → PATCH project), and each pays the cross-country latency.
  - Fix: Add vercel.json { "$schema": "https://openapi.vercel.sh/vercel.json", "regions": ["pdx1"] }. Hobby allows one region. Do not use sin1 because the user is in Singapore: that turns one browser round trip into four trans-Pacific Notion round trips. In step 1, add a timing probe in /api/health?probe=1 (behind login) to confirm.
- **[major]** It is unclear which DESIGN §12 'Next.js and security' amendments still apply. Taken literally, the DNS-rebinding host check ('proxy returns 421 for any Host other than localhost/127.0.0.1') would block every request on Vercel. The instrumentation.ts hourly backup cannot run on serverless. The Sec-Fetch-Site/Origin check for non-GET route handlers was quietly dropped, though route handlers get no built-in CSRF check from Next.
  - Fix: In ONLINE-ARCHITECTURE, list the §12 bullets one by one as kept, changed or removed. Remove the 421 host check when process.env.VERCEL is set (or allow VERCEL_PROJECT_PRODUCTION_URL and VERCEL_BRANCH_URL). Remove instrumentation-based backups in favour of the nightly job. Keep the Origin === host / Sec-Fetch-Site: same-origin check on POST /api/files and any other non-GET route handler.
- **[minor]** Retries are configured twice. The Notion SDK already retries (2 retries, Retry-After honoured up to 60 s, 60 s timeout). Wrapping it in the architecture's own 5-retry limiter can turn one slow call into minutes. That collides with Hobby's 300 s hard stop (504) and leaves batches half-applied.
  - Fix: Use one retry layer. Either new Client({ auth, notionVersion: '2025-09-03', timeoutMs: 20_000, retry: { maxRetries: 3, initialRetryDelayMs: 500, maxRetryDelayMs: 8_000 } }) with only a concurrency gate (p-limit 3) on top, or retry: false with the custom limiter. If Retry-After exceeds about 10 s, return 'busy, resuming' to the client-driven batch instead of sleeping. Set export const maxDuration = 60 on batch pages (it also applies to their Server Actions; never above 300 on Hobby).
- **[minor]** Client-driven batches interact badly with Next and Vercel behaviour. Server Actions run one at a time per tab, so a project-creation or sync batch blocks every edit until it finishes. Hobby has no Skew Protection, so a deploy during a batch (every merge to main) produces 'Failed to find Server Action'. When the session expires, the proxy redirects a Server Action POST, which surfaces as an opaque error, and the optimistic edit silently rolls back.
  - Fix: Show a modal progress UI during batches and disable edits. Catch 'Failed to find Server Action' and errors from the session check, reload, and resume from the persisted job cursor (Setup=Creating / Job record). In proxy.ts, answer requests carrying a 'next-action' header with 401 JSON instead of a redirect, and have the client show 'Session expired, sign in again' while keeping the queued change.
- **[minor]** The download design contradicts itself. A 302 to Notion's signed S3 URL cannot carry the app's Content-Disposition, inline allowlist, nosniff or CSP sandbox headers. Separately, the signed URL leaks through the Location header and Referer.
  - Fix: For files the app uploaded (≤4 MB), stream fetch(url).body through /api/files/[id] with the app's own headers (fits under 4.5 MB; streaming is not capped). Fall back to 302 for bigger files attached directly in Notion. Send Cache-Control: private, no-store and Referrer-Policy: no-referrer on both paths. Re-fetch the page on every download, because URLs expire after 1 h.
- **[minor]** Cron limits shape Phase 2 and any scheduled job. On Hobby, a cron runs at most once a day, somewhere within the hour, only on production, without retries, possibly twice, and never following redirects. 'A Vercel cron reads Outlook' therefore means one mail check per day. Whether crons pass 'All Deployments' Vercel Authentication is undocumented.
  - Fix: Say this in §7. Phase 2 needs Pro (per-minute crons), a manual 'Check mail' button, or a GitHub Actions schedule calling /api/cron/* with Authorization: Bearer CRON_SECRET plus x-vercel-protection-bypass. Exclude /api/cron from the proxy's session redirect, make the handler idempotent with a lock in Settings, record lastRunAt and lastError in Settings (Hobby keeps logs for 1 h), and test cron delivery with protection on.
- **[minor]** Notion mirrors can drift from the source of truth. The architecture invites browsing and filtering in Notion, but Value, State, Date, Progress, Current and Cells are mirrors the app re-derives. If the user edits State or Value in Notion, the milestone appears changed in Notion while the app ignores it and later overwrites it. Cached Library data hides direct edits too.
  - Fix: Tell the user: 'Notion is a view; change values in the app (Notes in Notion are fine).' Name mirror properties with a '(mirror)' suffix and lock the databases' schemas. Add a reconcile/rebuild action and the 60 s cache TTL.

### Implementation notes
- vercel.json: { "$schema": "https://openapi.vercel.sh/vercel.json", "regions": ["pdx1"] } (Hobby: exactly one region). Optional backup cron: "crons": [{ "path": "/api/cron/backup", "schedule": "17 18 * * *" }]. That is UTC; on Hobby it fires any time between 18:00 and 18:59 UTC, and only on production.
- Cron handler: if (!process.env.CRON_SECRET || request.headers.get('authorization') !== `Bearer ${process.env.CRON_SECRET}`) return new Response('Unauthorized', { status: 401 }). Add export const dynamic = 'force-dynamic'. Keep /api/cron out of the proxy's session redirect, because crons do not follow 3xx.
- src/proxy.ts (Next 16): export function proxy(request: NextRequest) { ... } plus export const config = { matcher: ['/((?!_next/static|_next/image|favicon.ico|robots.txt|login|api/health|api/cron).*)'] }. No 'runtime' export (it throws), and matcher strings must be literals. Requests with a 'next-action' header get Response.json({error:'session'}, {status:401}) instead of a redirect. Every Server Action and Route Handler still calls requireUser().
- Session (node:crypto + jose): key = crypto.hkdfSync('sha256', SESSION_SECRET, createHash('sha256').update(APP_PASSWORD).digest(), 'gpm-session-v1:' + (process.env.VERCEL_ENV ?? 'development'), 32). Sign with new SignJWT({ v: 1, epoch }).setProtectedHeader({ alg: 'HS256' }).setIssuedAt().setExpirationTime('30d').sign(new Uint8Array(key)); verify with jwtVerify(token, key, { algorithms: ['HS256'] }). Compare passwords with crypto.timingSafeEqual(sha256(input), sha256(APP_PASSWORD)) so the buffers have equal length. Cookie: name '__Host-gpm_session' with { httpOnly: true, secure: true, sameSite: 'lax', path: '/', maxAge: 2592000 }.
- Caching without cacheComponents: const getLibrary = unstable_cache(async (dsId: string) => ..., ['library', SCHEMA_VERSION], { tags: ['library'], revalidate: 60 }). Call updateTag('library') in Server Actions only, and revalidateTag('library', { expire: 0 }) in Route Handlers; the single-argument revalidateTag is deprecated. Do not call cookies()/headers() inside the cached function. If cacheComponents is ever enabled, every 'export const dynamic' must go, or the build errors.
- Next config: experimental: { serverActions: { bodySizeLimit: '2mb' } } (default is 1 MB). Uploads go through a Route Handler, never a Server Action. Put export const maxDuration = 60 on pages that run batches; it also applies to their Server Actions, and Hobby's cap is 300.
- Notion client: new Client({ auth: process.env.NOTION_TOKEN, notionVersion: '2025-09-03', timeoutMs: 20_000, retry: { maxRetries: 3, initialRetryDelayMs: 500, maxRetryDelayMs: 8_000 } }). The SDK retries 429/529 on every method and 500/503 only on GET/DELETE, so do not add a second retry loop. Wrap calls in a per-instance concurrency gate of 3; it is not global across Fluid instances. SDK namespaces: notion.dataSources.query/retrieve/update, notion.databases.create/retrieve/update, notion.pages.create/retrieve/update, notion.fileUploads.create/send/complete/retrieve/list.
- Upload route POST /api/files: const fd = await request.formData(); const f = fd.get('file') as File; reject if f.size > 4_000_000. const up = await notion.fileUploads.create({ mode: 'single_part', filename: f.name, content_type: f.type }); await notion.fileUploads.send({ file_upload_id: up.id, file: { filename: f.name, data: f } }); then within 1 hour pages.create on the Files & links data source with properties.File = { files: [{ type: 'file_upload', file_upload: { id: up.id }, name: f.name }] }. Check Origin/Sec-Fetch-Site manually, because Route Handlers get no CSRF check from Next.
- Download: pages.retrieve each time (file URLs expire after 1 h and must not be cached). For files ≤4 MB, stream (await fetch(url)).body with the app's own Content-Disposition (ASCII fallback plus filename*=UTF-8''…), nosniff and CSP sandbox. Otherwise Response.redirect(url, 302) with Cache-Control: private, no-store and Referrer-Policy: no-referrer.
- History hardening: properties Seq (number), Op id (rich_text), Prev hash and Hash (rich_text). Before creating, query History filtered by Op id to stay idempotent. After setup, call notion.databases.update({ database_id: historyDbId, is_locked: true }). Locking a single page needs a separate notion.pages.update({ page_id, is_locked: true }), because pages.create does not accept is_locked. Order rows by Seq, never by created_time, which is rounded down to the minute.
- Vercel dashboard checklist for the README: Deployment Protection → Vercel Authentication → 'All Deployments' (free on Hobby). Firewall → one rate-limit rule (path equals /login AND method POST, 10 per 10 min per IP, action 429). Functions → region pdx1. Env vars as Secret type: Production gets NOTION_TOKEN, APP_PASSWORD, SESSION_SECRET and CRON_SECRET. Preview gets a different NOTION_TOKEN and NOTION_PARENT_PAGE_ID pointing at the 'Gunnebo PM (Preview)' page. Redeploy after any env change. Rotating the Notion integration secret is the kill switch that disconnects every deployment at once.
- Automation behind protection: send the header 'x-vercel-protection-bypass: <VERCEL_AUTOMATION_BYPASS_SECRET>', plus 'x-vercel-set-bypass-cookie: true' for Playwright, against protected previews and production (GitHub Actions backups, e2e).
- Fake Notion: enable only when !process.env.VERCEL && !process.env.NOTION_TOKEN. On Vercel without a token, render the Setup page. Never write data/fake-notion.json on Vercel, because the filesystem is read-only apart from a per-instance /tmp.
- Notion limits to design around: 180 requests/min per connection (about 3/s), plus a separate ~3 rps for data source queries; 2000 characters per rich_text item; 100 items per array; 500 KB per payload; relations capped at 100 per request; files 5 MiB on Free; multi-part parts at least 5 MiB, so they cannot pass through Vercel's 4.5 MB body cap.
